# 从实现证据到审阅稿

```mermaid
flowchart TD
  A[源码、配置、明确指定的运行记录] --> B[快照与AST证据采集]
  B --> C[Agent精读：实现、启用、来源与效果]
  C --> D[特征与证据映射]
  D --> E[技术交底工作稿]
  D --> U[patent-bridge：两个固定版本上游技能]
  U --> V[可选权利要求、说明书、摘要与图源]
  V --> E
  E --> F[实现复核]
  F --> G[术语公式与流程复核]
  G --> H[反证与缺口复核]
  H --> I{阻断问题或需要修改?}
  I -- 是 --> J[修订特征、记录原因、生成新版本]
  J --> E
  I -- 否且至少两轮 --> K[冻结审阅稿与剩余限制]
  I -- 超预算 --> L[未完成稿与待确认问题]
  K --> M[发明人与专业人士确认]
  K --> W[上游流程图与Word转换器]
  W --> X[公式及页面QA]
  X --> M
```

模型端负责理解与写作；工具端负责记录与约束。Agent可根据复核问题调整下一步，默认按同一Agent的多视角串行工作，不要求多Agent并行、不自动联网调用模型。

交底与申请文件在同一manifest内冻结；申请review绑定全部文件哈希。Word由固定版本转换器处理，产出待页面核查的候选，失败图或公式不隐去。来源/许可证保留在vendor及THIRD_PARTY_NOTICES中。

区别于“论文改成专利”的地方：必须追到代码定义、调用入口、配置开关和具体数据流；技术方案按实现闭环建立，不把论文贡献列表或专利原稿当最终事实。公式与技术效果仍需实际核查，AST不替代技术判断。
